# Maintainability Notes

**Scope:** Storefront, admin, provider, vendor Partner OS, superadmin, and API.
**Relationship to security:** These are maintainability, operational-integrity,
and UX follow-ups. They are not launch-security findings and are not included
in the severity totals in [SECURITY_AUDIT.md](./SECURITY_AUDIT.md).

The items below are non-blocking hygiene work unless a change exposes a concrete
behavioral defect. Owners are role-based (not named individuals) because no
team roster is maintained here; assign a named DRI when scheduling an item.
Tests listed as "add" are acceptance criteria, not claims that coverage already
exists. Prefer doing this work alongside changes in the affected area.

| Priority | Owner (role) | Area | Remaining work | Regression tests / exit criteria |
|----------|--------------|------|---------------|----------------------------------|
| P2 | API / data | JSON-file writes | `backend/db/src/routes/client-categories.ts` reads the whole JSON file, appends in memory, then overwrites it. Concurrent admin POSTs can lose updates; `Date.now()` is not a collision-proof ID. The global API gate keeps this off the public route surface, so this is an integrity/operability risk rather than an auth defect. | Add/keep a concurrent-POST regression proving both updates survive and IDs remain unique; verify malformed/missing file behavior. Prefer a MySQL table, or serialize writes and use collision-resistant IDs plus atomic temp-file replacement. |
| P2 | Storefront + Provider frontend | Duplicated date/status helpers | Date parsing, SGT conversion, occurrence selection, and status presentation are independently implemented across apps. Consolidate only pure helpers behind an explicit offset-less Singapore-wall-clock contract; keep app-specific presentation local. | Add parity tests for bare SGT strings, ISO strings with offsets, invalid/null values, occurrence ordering and status mapping. Run under at least UTC and a non-UTC process timezone; retain `provider/src/utils/bookings.test.js` coverage. |
| P2 | API + Superadmin leads | Type safety (`any`) | A source scan found about 800 explicit TypeScript `any` annotations/casts, concentrated in the API and superadmin app. This weakens checks around SQL rows and API payloads. Reduce incrementally, starting at booking, payout and catalog boundaries; avoid broad casts at adapter edges. | `cd backend/db && npx tsc -p tsconfig.json --noEmit` and `cd superadmin && npx tsc -p tsconfig.json --noEmit`; add typed fixtures/compile-time checks for each migrated boundary and retain its runtime regression tests. |
| P2 | API + client-app leads | API DTO casing | Database/API fields are commonly `snake_case`; the customer context transforms them to `camelCase`, while provider code consumes raw `scheduled_at`/`booking_id` fields and other apps apply their own mappings. Define typed DTOs and normalize once per client without changing the public wire contract accidentally. | Extend `backend/db/scripts/test-public-catalog-dtos.mjs` and add contract fixtures for booking DTOs across storefront, provider, vendor and superadmin. Assert field names, nullability and date representation at the API boundary and client adapter. |
| P2 | Storefront, API/Vendor, Superadmin leads | Oversized modules | Current large files include `src/pages/ServiceDetail.jsx` (2,879 lines), `backend/db/src/routes/vendor.ts` (4,526), and `superadmin/src/pages/CatalogServices.tsx` (3,218). Their size raises review, test and regression costs; size alone is not a launch defect. Split by domain when nearby changes make it practical. | Before extracting, add/retain characterization coverage: storefront booking/recurrence/checkout flows; vendor route auth, scoping and job transitions; catalog editor load/save payloads. Run `npm run build` for affected apps and the API regression scripts relevant to each extracted route. |
| P3 | Provider + Superadmin product leads | Status semantics / labels | `provider/src/utils/bookings.js` contains a `confirmed` label, but the persisted booking status enum is `upcoming | completed | cancelled` and provider code does not currently use `confirmed`. In superadmin, overdue rows remain in the `Upcoming` count/tab and also receive a `Missed` badge. | Decide whether “Upcoming” means all open work or only future work; remove or formally support `confirmed`. Add tests for every persisted status label and for overdue rows' tab/count/badge behavior so the UI matches the decision. |
| Addressed | API / data | Uniqueness / idempotency | Vendor offer and job relationships now have database-level uniqueness safeguards. Existing duplicate rows are reported and safely detached from the repeated relationship (not deleted) before the migration adds the keys. Acceptance uses shared booking-lock/idempotency helpers; the offers inbox remains intentionally deferred for the single-vendor stage. | Apply `backend/db/migrations/023-vendor-offer-job-uniqueness.sql` after taking a database backup. From `backend/db`, build and run `node --test scripts/test-vendor-offer-uniqueness.mjs` to verify cleanup, retry, concurrent claim and duplicate-write behavior. |
| Addressed | Storefront + Provider frontend | Duplicated chat lifecycle | Customer and provider chat components share the abortable fetch/send/polling lifecycle through an app-neutral hook; each keeps its own auth/API adapter and presentation. The provider app authenticates with an HttpOnly session cookie, not a bearer token; 401 responses clear the session, and stale requests are aborted on close or booking changes. | Add regression tests for closing/switching bookings aborting stale work, send/poll using the right app adapter, and provider 401 expiring the session; keep them with the shared hook and adapter tests. |
| Addressed | Provider frontend | Contact and currency display | Provider booking cards validate phone strings before creating `tel:` links and show totals with Singapore-dollar formatting and a local currency icon. | Run `cd provider && node --test src/utils/phone.test.js`; retain coverage for malformed phone input and SGD formatting. |
